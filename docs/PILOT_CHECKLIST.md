# Чек-лист готовности к пилоту

Пилот: одна команда (по пулу выдачи — Builder Studio), одна неделя. Критерии успеха: все операции команды прошли через
портал; не было ошибок, которые исправляли вручную вне портала; занятость в Insight совпадает с фактической.

Команды на проде выполняются на сервере в каталоге проекта, с префиксом
`docker compose -f docker-compose.prod.yml exec backend` (ниже он опущен: `python -m app.cli …`). Значения в `.env`
меняются только по решению владельца, применяются командой `sudo ./scripts/deploy.sh --redeploy`.

## 1. Выкатка и окружение

- [ ] На проде последний коммит `main`, CI на нём зелёный: `GET /api/health` отдаёт `version` = sha коммита.
- [ ] `ENVIRONMENT=prod`, `AUTH_DEV_ENABLED=false`, свой `SECRET_KEY`, `COOKIE_SECURE=true`, права `.env` — 600.
- [ ] `DISPLAY_TIMEZONE` — имя IANA (`Asia/Novosibirsk`): с неизвестным именем портал не стартует, выкатка откатится сама.
- [ ] HTTPS работает, сертификат действует (до 20.03.2027; дата продления в календаре — 20.02.2027).
- [ ] Бэкап БД создаётся при выкатке: каталог `/var/backups/hms-rent`, последние 14, права `700`/`600`.
- [ ] Откат известен: `sudo ./scripts/deploy.sh --force-ref --ref <sha>`; миграции откат кода не отменяет
  (раздел 5 `docs/ARCHITECTURE.md` и техническая вики).

## 2. Люди и доступы

- [ ] **Отделы у пилотных сотрудников назначены** (Админка → «Сотрудники и отделы»): без отдела обычный сотрудник
  не может ничего заказать. Проверка: `python -m app.cli users` — у каждого пилотного сотрудника заполнен отдел.
- [ ] Пилотные сотрудники хотя бы раз вошли через Bouncer (учётка создаётся при первом входе) или заведены заранее
  («Добавить сотрудника заранее»).
- [ ] Администраторы: почты в `backend/config/admins.txt`; есть запасная локальная учётка (`python -m app.cli create-admin`).
- [ ] Исполнители: почты в `backend/config/executors.txt`, каждый вошёл и видит «Заказы на подготовку».
- [ ] Вход через Bouncer проверен реальной учёткой (в логе backend нет «id_token отклонён»).

## 3. Каталог и пул выдачи

- [ ] Пул Builder Studio (9 ПК: A65, A66, A82, A32, A38, A53, A319, A337, A338) опубликован и ограничен нужным отделом.
- [ ] Серверы пула в Insight со статусом «Ожидает» и атрибутом пула (`python -m app.cli push-pools`).
- [ ] Список ОС (`pc_os_list`) и типовых сборок (`pc_builds`) заполнен: «Настройки» → «Заказ физического ПК».
- [ ] Сотрудник пилотной команды видит ПК пула в каталоге, чужой отдел не видит.

## 4. Insight

- [ ] `INSIGHT_MODE=live`, токен сервисной учётки: `python -m app.cli insight-check --sample 5` без предупреждений.
- [ ] **Запись в Insight включена** («Настройки» → запись в Insight) после проверки на одном ПК: бронь → в Insight
  «Используется», команда, срок, номер заказа; возврат → «Ожидает».
- [ ] В админке «Требуют внимания» пусто или объяснимо; ошибки записи видны в «Инвентаризации».
- [ ] Свободные номера ВМ есть: блок «Номера ВМ» в «Обзоре парка» показывает остаток (предупреждение при 5 и меньше);
  проверка: `python -m app.cli insight-check --query 'objectType = "Automat" AND "Status" IN ("На складе") AND "Type" IN ("Virtual")' --sample 5`.

## 5. Виртуальные машины

- [ ] В «Настройках» указаны имена шаблонов ОС в vCenter, «Проверить» проходит без ошибок.
- [ ] Блок «Мощности кластера» в «Обзоре парка» показывает данные (чтение кластера разрешено сервисной учётке).
- [ ] Тестовая ВМ создаётся (пилотным пользователем или админом), получает IP, имя `A1###`, объект Insight переходит в
  «Используется», удаление возвращает «На складе».
- [ ] Готовые размеры (S, M, L) и лимиты (`vm_max_per_user`, диапазоны) соответствуют решению по пилоту.
- [ ] **DNS-записи ВМ не создаются** (DR-15392 отложена): заказчик подключается по IP, это нужно сказать пилотной группе.

## 6. Service Desk и уведомления

- [ ] `SD_TOKEN` задан, `python -m app.cli sd-check` показывает поля типов 1248 и 1252.
- [ ] Бронь тестового ПК создаёт заявку «подготовить ПК» со ссылкой на страницу заказа; возврат — заявку «Возврат ПК».
- [ ] `SD_SUMMARY_PREFIX` на проде пуст (иначе заявки получат «ТЕСТ» в теме, и исполнители не будут их брать).
- [ ] `MATTERMOST_WEBHOOK_URL` задан: в канал исполнителей приходят бронь, возврат, создание и ошибки ВМ.
- [ ] Ежедневная сводка просрочек и уведомления о сроке приходят после 10:00 в рабочий день (календарь
  `backend/config/work_calendar.yaml`: праздники 2026–2027; переносы января 2027 — после выхода постановления).

## 6а. Сквозная проверка (30 минут)

Выполняется до начала пилота тестовой парой «сотрудник + исполнитель».

1. Сотрудник бронирует ПК пула с ОС и сроком: ПК пропал из каталога, пришла заявка Service Desk со ссылкой, в канале
   сообщение о брони.
2. Исполнитель открывает заказ из заявки, вносит имя, IP, способ подключения: у сотрудника в колокольчике «ПК … готов»,
   в «Моей аренде» данные подключения.
3. Коллега сотрудника из того же отдела продлевает срок; пользователь из другого отдела заказ не видит.
4. Срок дольше 3 месяцев: заказ встал на максимум, администратору пришла заявка в «Сроки аренды», решение пришло
   сотруднику уведомлением.
5. Сотрудник возвращает ПК: заявка «Возврат ПК», ПК снова в каталоге, в Insight «Ожидает».
6. Заказ ВМ: создание, IP, уведомление, продление, удаление.
7. «Сообщить о проблеме» создаёт заявку, ответ агента виден в «Моей аренде».

## 7. Инструкции и договорённости

- [ ] Пилотной группе отправлена инструкция для заказчиков (`docs/INSTRUCTION_CUSTOMER.md`), исполнителям —
  `docs/INSTRUCTION_EXECUTOR.md`.
- [ ] Исполнители знают, что вне портала остаётся: установка ОС, DNS-запись ПК, закрытие заявок Jira, «Неисправен» и
  отклонение (кнопок пока нет), стандартный пароль сообщают заказчику лично.
- [ ] Назначены ответственные: кто следит за каналом исполнителей, кто отвечает на заявки по проблемам, к кому эскалировать
  (старший — Кирилл Champion).
- [ ] Известно, где смотреть при сбоях: логи (`make logs`, на проде `docker compose -f docker-compose.prod.yml logs backend worker`),
  «Логи системы» и «Требуют внимания» в админке.

## 8. Что смотреть в течение пилота

| Когда | Что |
|---|---|
| Каждый день | «Обзор парка» (занятость, «Требуют внимания», номера ВМ, мощности), канал исполнителей, раздел «Заказы на подготовку» |
| Каждый день после 10:00 | Сводка просрочек, «Сроки аренды»: просрочки и заявки на срок |
| После каждой выкатки | `/api/health`, вход через Bouncer, одна бронь и один возврат |
| В конце недели | Сверка критериев успеха: операции только через портал, ручные правки, расхождения с Insight (Инвентаризация → «Требуют внимания») |

## Известные ограничения на пилоте

* DNS-записей ВМ нет (DR-15392), для физических ПК запись создаёт исполнитель вручную.
* Нет задач «Подготовить комплект» в Jira и статусов заказа «Принят/В работе/Выполнен»; работа идёт по заявкам Service Desk.
* Нет отмены заказа ПК (есть возврат), кнопок «Неисправен» и «Пересоздать», отклонения заказа с основанием.
* Нет контроля нормативов времени и уведомлений «не взята за час».
* Личных сообщений в Mattermost и почты нет: заказчик получает уведомления в колокольчике портала.
* Одна ВМ создаётся за раз (без параллельных клонов): очередь большого числа ВМ идёт последовательно.
