# Вход сотрудников через корпоративный SSO (Bouncer)

Сотрудник нажимает кнопку входа на странице логина, авторизуется в Bouncer — и он в портале. Пароли портал не
хранит. Используется стандартный протокол OpenID Connect (authorization code flow).

## Что нужно для подключения

В Bouncer должен быть заведён клиент для портала — это делают администраторы Bouncer. Им нужно передать
**redirect URI**, а от них получить четыре значения:

| Что получить | Куда вписать |
|---|---|
| Адрес авторизации (authorize endpoint) | `BOUNCER_AUTHORIZE_URL` |
| Адрес обмена кода на токен (token endpoint) | `BOUNCER_TOKEN_URL` |
| Идентификатор клиента | `BOUNCER_CLIENT_ID` |
| Секрет клиента | `BOUNCER_CLIENT_SECRET` |

**Redirect URI**: `<PUBLIC_URL>/api/v1/auth/bouncer/callback`, например
`https://hmsrent.<ваш-домен>/api/v1/auth/bouncer/callback`. Для локального запуска —
`http://localhost:8080/api/v1/auth/bouncer/callback`, при `npm run dev` — `http://localhost:5173/...`.
Запрашиваемые права (scope): `openid profile email`.

## `.env`

```env
PUBLIC_URL=https://hmsrent.<ваш-домен>
BOUNCER_AUTHORIZE_URL=
BOUNCER_TOKEN_URL=
BOUNCER_CLIENT_ID=
BOUNCER_CLIENT_SECRET=
# BOUNCER_ISSUER=      # необязательно: ожидаемый iss в id_token, пусто — не проверять
COOKIE_SECURE=true
```

`PUBLIC_URL` должен совпадать с адресом, по которому открывают портал: из него собирается redirect URI, и он
должен **буква в букву** совпасть с тем, что зарегистрирован в Bouncer (схема, домен, путь).

Применить правку `.env`: на проде — `sudo ./scripts/deploy.sh --redeploy`, при разработке —
`docker compose up -d --force-recreate backend worker`.

Проверка: на странице входа появляется кнопка входа через Bouncer. Если не заданы `BOUNCER_AUTHORIZE_URL`,
`BOUNCER_TOKEN_URL` или `BOUNCER_CLIENT_ID`, в логе backend при старте будет предупреждение
«Вход через Bouncer выключен». Для включения кнопки также нужен `BOUNCER_CLIENT_SECRET`.

## Откуда берётся логин

Из `id_token` портал берёт первое непустое значение по порядку: `email`, `preferred_username`, `upn`, `sub`
(без учёта регистра). Это же значение становится логином сотрудника; почтой оно считается, если содержит `@`.
Имя для отображения — claim `name`, затем `given_name`, иначе часть логина до `@`. Фото профиля портал не получает,
поэтому показываются инициалы.

Подпись `id_token` портал не проверяет: токен приходит напрямую от token endpoint по защищённому каналу
(back-channel), как допускает OpenID Connect для code flow. Проверяются срок действия (`exp`), `nonce`, получатель
токена `aud` и, если задан `BOUNCER_ISSUER`, издатель `iss`:

- `aud` (строка или список) должен содержать `BOUNCER_CLIENT_ID`; без этого claim вход невозможен;
- `BOUNCER_ISSUER` необязателен: пусто — `iss` не проверяется, иначе должен совпасть с токеном буква в букву.

> **Внимание при обновлении.** Проверка `aud` появилась позже первого запуска, а реальный ответ Bouncer в тестах
> эмулируется. После выкатки обязательно проверьте реальный вход. Если `aud` в токене Bouncer отличается от
> `BOUNCER_CLIENT_ID` (например, содержит другой идентификатор или отсутствует), вход сломается: пользователь увидит
> «Сессия входа некорректна…», а в логе backend будет строка «id_token отклонён: aud=… не содержит client_id=…» с
> полученным и ожидаемым значениями (сам токен в лог не пишется). Тогда сверьте `BOUNCER_CLIENT_ID` с клиентом в Bouncer
> или уточните у его администраторов, какое значение попадает в `aud`. Для `BOUNCER_ISSUER` в логе будет
> «iss=… , ожидался BOUNCER_ISSUER=…»: возьмите значение `iss` оттуда.

## Администраторы

Два варианта, можно совмещать:

| Вариант | Как | Плюсы |
|---|---|---|
| **Через Bouncer** (основной) | рабочая почта в `backend/config/admins.txt`, по одной в строке | личные учётки: в журнале видно, кто из админов что сделал; файл перечитывается на лету — добавили или убрали почту, и права меняются без перезапуска |
| **Локальная учётка** | `docker compose exec backend python -m app.cli create-admin <логин> --name "Имя"` (на проде — `sudo docker compose -f docker-compose.prod.yml exec …`) — пароль вводится в консоли | работает, даже если Bouncer недоступен; удобно как «аварийный» вход |

Почта в `admins.txt` сравнивается без учёта регистра с любым из значений `email`, `preferred_username`, `upn`, `sub`
из токена. Локальные учётки: `set-password <логин>`, `disable <логин>`, `enable <логин>`, `users` — список всех.
Форма входа для них — «Вход для администраторов» на странице входа (`AUTH_LOCAL_ENABLED=true`).
После серии неудачных попыток логин блокируется на время (`LOGIN_MAX_ATTEMPTS`, `LOGIN_LOCK_MINUTES`; значения по
умолчанию — в `.env.example`).

## Исполнители

Рабочая почта исполнителя — в `backend/config/executors.txt` (`EXECUTORS_FILE`), по одной в строке, так же как
`admins.txt`: файл перечитывается на лету, почта сравнивается без учёта регистра. Исполнитель входит через Bouncer и
видит раздел «Исполнитель» (очередь выданных ПК и страница заказа), админки у него нет. Администраторам раздел доступен
и без этого файла; почта в обоих файлах даёт права администратора. Сравнивается почта (или логин, если почты нет), а не
все значения токена, как у `admins.txt`.

## Типичные ошибки

При сбое портал возвращает пользователя на страницу входа с сообщением:

| Сообщение | Причина |
|---|---|
| «Вход отменён» | пользователь отказался на стороне Bouncer |
| «Сессия входа устарела, попробуйте ещё раз» | вход начат больше 10 минут назад, не совпал `state` или `nonce`, истёк срок токена или пропала cookie |
| «Сервер авторизации (Bouncer) отклонил запрос» | token endpoint ответил не 200: неверный `BOUNCER_CLIENT_ID` или `BOUNCER_CLIENT_SECRET`, redirect URI не совпал с зарегистрированным |
| «Сервер авторизации (Bouncer) недоступен, попробуйте позже» | token endpoint не отвечает или таймаут (10 с) |
| «Сессия входа некорректна, обратитесь к администратору портала» | `aud` токена не содержит `BOUNCER_CLIENT_ID` или `iss` не совпал с `BOUNCER_ISSUER`; причина и значения — в логе backend |
| «Bouncer вернул некорректный ответ» / «…некорректный id_token» | ответ не JSON (например, страница ошибки прокси) или токен не разбирается |
| «Bouncer не вернул id_token» | клиент в Bouncer настроен без `openid` |
| «Bouncer не передал email или логин пользователя» | в токене нет ни одного из полей `email`, `preferred_username`, `upn`, `sub` |
| «Учётная запись отключена администратором портала» | сотрудник заблокирован на странице «Сотрудники» |
| «Этот логин принадлежит локальной учётке администратора» | логин совпал с локальной учёткой, входить нужно через форму для администраторов |
