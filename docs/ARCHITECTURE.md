# Архитектура HMS Rent

## Компоненты

```
 Браузер ──► frontend (nginx: SPA, прокси /api, HTTPS) ──► backend (FastAPI) ──► PostgreSQL
                                                                │  ▲                 ▲
   Bouncer ◄── вход (OIDC) ─────────────────────────────────────┤  │                 │
   Jira Service Desk ◄── создание заявок и переписка ───────────┘  │                 │
                                                                    │                 │
   Jira Insight ◄── чтение и запись ─┐                              │                 │
   Jira Service Desk ◄── статусы ────┼──────────────── worker ──────┴─────────────────┘
   vCenter ◄── клон и удаление ВМ ───┤        (синхронизация, запись в Insight, очередь ВМ,
   Mattermost ◄── уведомления ───────┘         статусы заявок, сводка просрочек)
```

* **backend** — REST API `/api/v1/*`. Работает одним процессом: троттлинг неудачных входов и кэш настроек с сайта лежат
  в памяти процесса, поэтому несколько копий не поддерживаются (прод — одна ВМ). При старте контейнера применяет
  миграции (`alembic upgrade head`).
* **worker** — один процесс с тремя независимыми циклами (раз в 5 секунд каждый), чтобы долгое клонирование ВМ (до
  часа) не останавливало остальное. Ошибка шага пишется в лог и не останавливает цикл:
  1. цикл Insight и заявок, шаги по очереди:
     1. синхронизация с Insight (если подошло время, защищена advisory-lock в Postgres, поэтому кнопка «Синхронизировать
        сейчас» во время планового прогона ничего не ломает);
     2. запись изменений в Insight;
     3. обновление статусов заявок Service Desk (раз в 2 минуты на заявку);
     4. ежедневная сводка просрочек и напоминания о конце срока в Mattermost;
  2. цикл создания ВМ: берёт заявки из очереди по одной, пока она не опустеет;
  3. цикл удаления ВМ: до 5 удалений за круг, обновление IP и срока в Notes. Циклы ВМ запускаются, только если настроен vCenter;
     при старте перед ними восстанавливаются записи `creating`.
* **frontend** — статическая сборка React, nginx отдаёт её и проксирует `/api` на backend (locations и gzip — в
  `frontend/nginx/app.inc`, один файл для http и https). Если на сервере есть
  сертификат, nginx принимает HTTPS (подробности в «Доставка и окружения»).

## Структура backend

Зависимости идут сверху вниз: `api/routes` → `services` → `schemas`, `models`, `integrations`, `db`, `core`.

* **`api/routes`** — тонкий слой HTTP: разбор запроса, права (`CurrentUser` / `AdminUser`), вызов сервиса, ответ.
  Запросов к БД и бизнес-правил нет; файлы маршрутов: `auth`, `catalog`, `bookings`, `vms`, `requests`, `admin`,
  `admin_extra`, `admin_ops`.
* **`services`** — бизнес-логика и работа с БД, один модуль на область:

  | Область | Модуль |
  |---|---|
  | вход, SSO-сотрудники; троттлинг неудачных входов (в памяти процесса) | `auth`, `auth_throttle` |
  | каталог для сотрудников | `catalog` |
  | брони, продление и возврат (+ фоновые задачи после ответа: запись в Insight, заявка на возврат) | `bookings` |
  | права на заказы: автор, участник команды заказа, администратор; условие «заказы пользователя и команды» для списков | `access` |
  | пулы выдачи (список со статистикой, создание, правка, назначение ПК) | `pools` |
  | справочник отделов, проверка «отдел существует / активен» | `departments` |
  | сотрудники в админке | `users` |
  | карточка ПК в админке, инвентаризация, сводка, журналы, CSV | `computers`, `inventory` |
  | синхронизация с Insight, её журнал и детали запуска, запись обратно | `sync`, `sync_runs`, `writeback` |
  | ВМ: конструктор, очередь worker'а, проверка vCenter | `vms`, `vm_jobs` |
  | заявки Service Desk | `service_requests` |
  | сроки аренды: просрочки, ежедневная сводка, журнал продлений ПК и ВМ и «Принято» | `overdue` |
  | лимит срока аренды (3 месяца) и заявки админу на больший срок: расчёт, список, согласование, отказ | `term_limit`, `term_requests` |
  | настройки с сайта (`app_settings`) | `runtime` |

  Бизнес-ошибки — `NotFound`, `Conflict`, `Forbidden`, `Unauthorized`, `Unprocessable`, `TooManyRequests` из
  `core/errors.py`; в HTTP-ответ их превращает `main.py`. Нарушение уникального индекса при записи превращается в
  `Conflict` через `db/integrity.conflict_on_integrity_error`.
* **`schemas`** — все pydantic-схемы API (по областям: `admin`, `booking`, `computer`, `department`, `service_request`,
  `settings`, `user`, `vm` …); в роутах и сервисах своих схем нет.
* **`models`** — SQLAlchemy 2 (async). Перечисления лежат в `models/enums.py` (`StrEnum`): `ComputerStatus`,
  `BookingStatus`, `VmStatus`, `SyncRunStatus`, `ServiceRequestKind`, `EventType`, `Tier`, `UserRole`. В БД они хранятся
  обычными строками (колонки `String`), поэтому значения менять нельзя без миграции.
* **`integrations`** — внешние системы за узкими интерфейсами: `InsightSource` (живой клиент и mock), vSphere,
  Service Desk, Bouncer, Mattermost.

## Кто источник правды

| Данные | Источник | Почему |
|---|---|---|
| Список ПК, характеристики, «железный» статус (свободен / ремонт / списан) | **Insight** | там уже ведётся учёт, портал его не дублирует вручную |
| Бронирования: отдел, ответственный, даты | **БД портала** | история выдачи и инвентаризация по отделам |
| Виртуальные машины | **vCenter** (сама ВМ) и **БД портала** (заявка, владелец, статус) | ВМ создаёт и удаляет worker, в БД остаётся история |
| Статус заявки в Service Desk и публичные комментарии | **Jira** | портал хранит ключ заявки и последний известный статус, комментарии читает по запросу |
| Справочник отделов | **БД портала** | выбор из списка, а не свободный текст: отчёты не разваливаются на «QA» / «qa» / «Отдел QA» |
| Шаблоны ОС для конструктора ВМ, лимиты и интервалы | настройки на сайте (`app_settings`) | админ меняет без перезапуска, значения важнее `.env` |
| Роль администратора | файл `config/admins.txt` (рабочие почты из Bouncer) или локальная учётка из CLI | файл проверяется на каждом запросе: убрали почту — права пропали сразу |
| Что видно сотрудникам | **пулы выдачи** в БД портала | Insight не надо менять; админ управляет из интерфейса |

## Модель данных

| Таблица | Что хранит |
|---|---|
| `computers` | копия объекта Insight: характеристики, `insight_status`, все атрибуты в `attributes` (JSONB), категория `tier`, статус портала `status`, текущий отдел, `usage_until` и `order_number` текущей аренды |
| `bookings` | бронь: **номер заказа** (сквозной, общий с ВМ), ПК, отдел (команда заказа), аккаунт, имя и ник, цель, `booked_at`, `expected_return_at` (обязателен для новой брони, у старых может быть пустым), `os_label` (ОС, которую поставит исполнитель), `returned_at`, кто вернул и комментарий |
| `booking_extensions` | журнал продлений ПК и ВМ (имя осталось от первой версии): ровно одно из `booking_id` / `vm_id` (CHECK в БД, миграция 0009), кто продлил, срок было → стало (`old_return_at` пуст у заказов без срока), причина, `created_at`; `acknowledged_at` и `acknowledged_by_id` — кто из админов отметил «Принято» |
| `term_requests` | заявка админу на срок дольше лимита: ровно одно из `booking_id` / `vm_id`, кто просит, запрошенный срок, причина, статус (`pending` / `approved` / `rejected`), кто и когда решил; у одного заказа ждёт решения не больше одной (частичные уникальные индексы, миграция 0010) |
| `virtual_machines` | заявка на ВМ и её жизненный цикл: имя, CPU, RAM, диск, статус, шаблон ОС (`template_key`, `os_label`, `os` — от него зависит способ подключения), автор, отдел (команда заказа), срок `expected_return_at` (обязателен для новой ВМ, у старых может быть пустым), `notes_return_at` (срок, записанный сейчас в Notes ВМ в vCenter, миграция 0011), `insight_object_id`, `insight_object_type_id`, `insight_pending` (объект Insight, чей номер стал именем ВМ, и флаг записи в него; миграция 0012), `vsphere_moid`, IP |
| `service_requests` | заявки в Jira Service Desk: вид (`problem` / `return` / `prepare` / `build`), ПК или ВМ, у сборки — команда `department_id`, ключ заявки, последний известный статус, ошибка создания |
| `asset_events` | журнал всего, что происходило с ПК: бронь, возврат, смена статуса в Insight, появление/исчезновение, правки админа, ошибки записи |
| `departments` | справочник отделов (название, код, руководитель, активен) |
| `pools`, `pool_departments` | пулы выдачи и отделы, которые их видят; `computers.pool_id` — в каком пуле ПК (нет пула — сотрудники его не видят) |
| `users` | сотрудники, создаются при первом входе (логин, ФИО, почта, роль, отдел, `auth_source`: `bouncer` / `local` / `dev` / `microsoft`; `microsoft` — сотрудники, заведённые заранее администратором («Сотрудники → Добавить сотрудника заранее»), и старые записи) |
| `sync_runs` | журнал синхронизаций с Insight; `details` (JSONB) — что именно изменилось в запуске |
| `app_settings` | настройки с сайта (ключ → JSON), в том числе список шаблонов ОС `vm_templates` |

Номера заказов даёт последовательность `rental_order_seq`: общая для ПК и ВМ, пропуски возможны.

## Права на заказы

Все участники команды имеют равные права на её заказы. **Команда заказа** — отдел брони или ВМ (`department_id`, его
выбирает автор в форме), **команда пользователя** — `users.department_id`. Просмотр, продление, возврат ПК и отмена
ВМ доступны автору заказа, участнику той же команды (отдел совпадает и не пуст) и администратору; пользователь без
отдела видит только свои заказы. Правило одно на все области и лежит в `services/access.py`: `can_access`,
`ensure_access` (403 «… может тот, кто бронировал ПК / заказывал ВМ, участник его команды или администратор») и
`mine_or_team` (SQL-условие для списков: «Моя аренда» — `GET /bookings/my`, `GET /vms/my` — и доступ к заявкам Service
Desk). В журналах (`returned_by`, `released_by_id`, продления) хранится тот, кто действовал, а не автор заказа.
Создавать заказы от имени команды по-прежнему может любой сотрудник, правила создания не менялись.

Ограничение в БД: **у одного ПК не может быть двух активных броней** (частичный уникальный индекс
`uq_bookings_active_computer`), а сама бронь делается под `SELECT … FOR UPDATE` — двое не смогут
одновременно забрать один компьютер.

## Статусы компьютера на портале

| Статус | Откуда | В каталоге |
|---|---|---|
| `available` | Insight: «Ожидает» и нет активной брони | ✅ можно бронировать |
| `booked` | есть активная бронь на портале | — |
| `in_use` | Insight: «Используется», «В работе», «Исследования», «Проекты», «проект Events», «Эко», а брони нет (выдан мимо портала) | — |
| `maintenance` | Insight: «ТО», «Тест», «Резерв», «На складе», «Доставка», «На регистрации», «Frozen» | — |
| `retired` | Insight: «К закрытию», «Закрывается», «Закрыто», «Списано» | — |
| `unknown` | статус Insight не описан в `status_map` | — |

Соответствие статусов настраивается в `backend/config/insight_mapping.yaml`. Статус «железа»
меняется в Insight, портал только читает его. Исключение — запись в Insight при брони (ниже).

## Пулы выдачи

Синхронизация тянет из Insight всю «вселенную» по `query` — её видят только админы в инвентаризации.
Сотрудникам в каталоге показываются лишь ПК из **опубликованных пулов**. Пул наполняется списком
имён/ключей Insight или галочками в инвентаризации; ПК состоит максимум в одном пуле, каждое
перемещение пишется в журнал ПК. Скрыть пул — значит мгновенно убрать его ПК из каталога, не трогая брони.
Пул без отделов виден всем сотрудникам, с отделами — только им.

## Синхронизация (Insight → портал)

1. Worker раз в `insight_sync_interval_min` (настройка на сайте, по умолчанию 10 минут) забирает все объекты по
   запросу `query` из маппинга (с пагинацией).
2. Объекты сопоставляются с `computers` по `insight_object_id`, характеристики обновляются.
3. Если поменялся статус в Insight — пишется событие `insight_status_changed`.
4. ПК, пропавшие из выборки, **не удаляются**, а помечаются `is_archived` (история сохраняется).
5. Защита от ошибки в запросе: если Insight вернул 0 объектов, а в базе они есть, прогон
   считается ошибочным и ничего не архивирует.
6. Что изменилось в запуске, сохраняется в `sync_runs.details`: новые ПК, изменённые (поле: было → стало) и
   ушедшие в архив (до 500 записей на список; служебные атрибуты Insight вроде `Updated` не учитываются). На странице
   «Синхронизация» счётчики «Новых / Изменено / В архив» открывают эти детали (`GET /admin/sync/runs/{id}`).

## Обратная запись (портал → Insight), настройка `insight_writeback`

При брони/возврате у ПК ставится флаг `writeback_pending`. Worker в каждом круге (раз в 5 с) отправляет в Insight
**текущее** состояние: статус («Используется» / «Ожидает»), «Пул выдачи», «Команда-получатель»,
«Срок использования», «Номер заказа» (имена атрибутов — в `insight_mapping.yaml`, подробности — INSIGHT_SETUP.md, раздел 7) и снимает флаг. Если Insight недоступен, флаг остаётся и запись
повторится; ошибка видна в карточке ПК и в «Требуют внимания». Отправка идемпотентна: повтор ничего не испортит.
Запись состояния ВМ в их объекты Insight описана в разделе про виртуальные машины.

## Виртуальные машины и шаблоны ОС

Конструктор ВМ (карточка в каталоге) ставит заявку в очередь, worker создаёт машину в vCenter.

* **Жизненный цикл:** `queued → creating → ready → deleting → deleted`, ошибка — `failed`. Из `queued` отказ сразу
  `deleted`, из `ready` — через `deleting` (worker выключает и удаляет ВМ в vCenter по `vsphere_moid`). ВМ без `moid`
  (из очереди или `failed`) в vCenter не создавалась, поэтому отказ сразу даёт `deleted`: по имени ВМ не удаляются
  никогда, имя могла занять чужая ВМ. Из `creating` отказаться нельзя.
* **Создание:** worker клонирует шаблон из `vm_templates`, задаёт CPU, RAM, диск и описание (арендатор, отдел, срок).
  При ошибке делается **одна повторная попытка** через 10 секунд; клиент vSphere сам удаляет недоделанный клон (по
  объекту, а не по имени); после второй неудачи ВМ получает статус `failed` с текстом ошибки. Если шаблон ОС заявки
  убрали из настроек или стёрли его имя, заявка сразу получает `failed` («Шаблон ОС … больше не доступен»), а не
  создаётся из шаблона по умолчанию.
  О неудаче создания (после второй попытки или из-за пропавшего шаблона) worker пишет в канал Mattermost, текст ошибки
  обрезается до 300 символов.
* **Мощности кластера.** Перед клоном worker читает использование кластера из vCenter (`GetResourceUsage`) и, если
  свободной памяти или места в хранилище меньше, чем просит ВМ, сразу ставит `failed` с текстом «Недостаточно
  мощностей кластера, не хватает …» без повторной попытки и пишет в канал. Процессор не проверяется: переподписка по
  ядрам допустима. Если сам vCenter на проверку не ответил, ВМ создаётся как обычно (ошибку даст клон).
  `GET /admin/cluster` отдаёт те же данные для «Обзора парка» (`ok=false` и причина, если vCenter не подключён или не
  отвечает).
* **Шаблоны ОС** (`vm_templates` в `app_settings`, редактор в «Настройках»): ключ, название, ОС (`windows` / `linux`),
  имя шаблона в vCenter, спецификация гостевой настройки, минимальный диск, включён или нет. Шаблон без имени в
  vCenter показывается в конструкторе как «скоро» и недоступен для выбора. Диск не может быть меньше минимума
  шаблона и общего `vm_min_disk_gb`. Ключи шаблонов уникальны; `PATCH /admin/settings` с повторным ключом или
  неизвестной настройкой отклоняется (422).
* **Готовые размеры** (`vm_sizes` в `app_settings`, редактор в «Настройках»; по умолчанию S 2/4/50, M 4/8/100,
  L 8/16/200): кнопка в конструкторе ставит ядра, память и диск, ползунки остаются для своей конфигурации. Названия
  уникальны; размер вне лимитов конструктора в `GET /vms/options` (`sizes`) не отдаётся.
* **Ограничения:** лимит ВМ на человека (`vm_max_per_user`, считается по автору, а не по команде), диапазоны CPU, RAM и
  диска (настройки на сайте). Имя уникально среди ВМ не в статусах `deleted` и `failed`.
* **Имя и номер ВМ.** Имя не вводится: при заказе портал берёт свободный объект Insight (`vm_free_query`: тип Virtual,
  статус «На складе»), не занятый живой ВМ, с наименьшим номером; его имя (`A1###`) становится именем ВМ в vSphere и
  на портале, id объекта хранится в `insight_object_id`. Выбор идёт под advisory-lock (после сетевого запроса к
  Insight), а уникальный индекс не даёт одному объекту достаться двум живым ВМ. Нет свободных номеров или Insight
  недоступен — заказ отклоняется (409) с понятным текстом. Номер освобождается при удалении ВМ и при `failed`.
  У прежних ВМ (`rent-…`) объекта нет.
* **Запись в Insight.** При `insight_writeback` worker (цикл Insight, шаг «Запись ВМ в Insight», до 20 ВМ за круг,
  флаг `insight_pending`) пишет в объект ВМ: живая — «Используется», команда, срок, номер заказа, IP; удалённая или
  `failed` — «На складе» и пустые поля, если объект не занят другой живой ВМ. Флаг ставится при заказе, готовности,
  смене IP, продлении, согласовании срока, удалении и ошибке. Сбой записи оставляет флаг, повтор на следующем круге.
* **Данные подключения:** в ответе по ВМ есть `connection_login` (всегда `user`, пароль в портале не хранится) и `connection_method`: RDP для Windows, VNC для Linux (по `os`, который записывается из шаблона при заказе; у старых ВМ выводится из названия ОС, для неизвестной ОС способ пуст). «Моя аренда» показывает их у готовой ВМ рядом с IP.
* **Срок использования** обязателен в форме заказа, как и у ПК (`expected_return_at`, не в прошлом; иначе 422). У ВМ,
  созданных до этого правила, срок может быть пустым. Срок можно продлить (ниже).
* После перезапуска worker'а записи `creating` сверяются с vCenter по имени: нашлась — `ready`, нет — снова `queued`.

## Заявки в Jira Service Desk

Подробности настройки — `docs/SERVICE_DESK.md`. Включается заданным `SD_TOKEN` (или `SD_USERNAME`/`SD_PASSWORD`);
без него кнопки скрыты.

* **«Сообщить о проблеме»** у ПК и ВМ в «Моей аренде»: backend создаёт заявку типа `SD_REQUEST_TYPE_PROBLEM` с описанием
  проблемы и данными ПК или ВМ (имя, заказ, команда, арендатор, характеристики).
* **Возврат ПК** на сайте в фоне создаёт заявку типа `SD_REQUEST_TYPE_RETURN` (`SD_RETURN_ON_RETURN`). Название:
  `HMS Rent: возврат ПК <имя> (заказ №N)`. Ошибка Jira не мешает возврату и сохраняется в заявке.
* **Подготовка ПК после брони** (временный мост до задач «Подготовить комплект», DR-15072): при брони заказчик выбирает
  ОС из списка `pc_os_list` («Настройки» → «Заказ физического ПК», по умолчанию — список DR-15064), она пишется в
  `bookings.os_label`; в фоне создаётся заявка типа `SD_REQUEST_TYPE_ORDER` («Прочее») `HMS Rent: подготовить ПК <имя>
  (заказ №N)` с ОС, данными ПК и целью (`SD_PREPARE_ON_BOOKING`). Ошибка Jira бронь не отменяет и сохраняется в заявке.
* **Сборка по запросу:** карточка в каталоге (видна при подключённом Service Desk) → форма: типовая сборка из `pc_builds`
  (DR-15062, «тип — состав») или своя конфигурация, ОС, команда, арендатор, срок, необязательные «нужен к» (не раньше
  завтра) и цель (`POST /requests/build`). Создаётся заявка `SD_REQUEST_TYPE_ORDER` `HMS Rent: сборка ПК — тип A (заказ №N)`
  с номером заказа из общей последовательности; срок дольше 3 месяцев помечается «нужно согласование администратора».
  Заявка привязана к команде (`department_id`) и видна в «Моей аренде» в блоке «Сборки по запросу». Собранный ПК
  исполнитель заводит в Insight и выдаёт вне портала (до интерфейса исполнителя, DR-15075). Варианты для форм —
  `GET /catalog/order-options`.
* **От чьего имени:** сначала `raiseOnBehalfOf` = логин сотрудника; если такого пользователя в Jira нет, заявка
  создаётся от сервисной учётки, а имя и почта сотрудника попадают в описание.
* **Переписка:** публичные комментарии из Jira видны в портале (внутренние заметки агентов скрыты), ответ сотрудника
  уходит публичным комментарием `[HMS Rent] Имя: текст`. Статус открытых заявок worker обновляет раз в 2 минуты.
* **Доступ:** заявку видят и комментируют её автор, автор и участники команды заказа и администраторы (правило —
  «Права на заказы»).

## Сроки аренды: просрочки и продления

Бронь ПК с активным статусом и ВМ в статусах `ready` / `failed` считаются просроченными, если срок возврата раньше
сегодняшнего дня (по `DISPLAY_TIMEZONE`). Админка → «Сроки аренды» показывает их по убыванию дней просрочки; у ПК
и ВМ можно продлить срок, у ПК — ещё написать арендатору или вернуть бронь.

**Лимит срока и заявки на срок.** Без согласования админа ПК и ВМ можно взять не дольше чем на 3 месяца
(`MAX_TERM_MONTHS` в `services/term_limit.py`, на frontend — `lib/utils.ts`). При заказе лимит считается от сегодня,
при продлении арендатором или его командой — от текущего срока возврата (у просроченного заказа — от сегодня). Если
выбрана дата дальше, заказ оформляется или продлевается на максимум, а в `term_requests` создаётся заявка на нужный срок;
пока она ждёт решения, вторая заявка по этому заказу не принимается (409). Админа лимит не ограничивает. В «Сроки аренды»
блок «Заявки на срок» (`GET /admin/term-requests`): админ согласует заявку (`POST /admin/term-requests/{id}/approve`,
необязательное `approved_return_at` — своя дата) или отклоняет (`/reject`, остаётся максимальный срок). Согласование
ставит срок как продление админа (журнал `booking_extensions`, `usage_until` и Insight у ПК, событие `extended`).
Заявки по возвращённым ПК и удалённым ВМ не показываются. Арендатор видит у заказа `requested_return_at`, пока заявка
ждёт решения.

**Продление ПК.** Срок возврата при брони обязателен. Арендатор, участник его команды или админ продлевает аренду
в «Моей аренде» или на странице «Сроки аренды» (`POST /bookings/{id}/extend`). Новый срок не в прошлом и позже текущего
(у старых броней без срока — с сегодняшнего дня), причина необязательна. Продление сразу меняет `expected_return_at`,
`usage_until` ПК и «Срок использования» в Insight (при включённой записи), пишет событие `extended` в историю ПК и
строку в `booking_extensions`. Количество продлений не ограничено. Продление арендатора или его команды считается новым,
пока админ не нажмёт «Принято» (`POST /admin/extensions/{id}/ack`); продление админа сразу принято им. Блок «Продления»
(`GET /admin/extensions`) показывает новые сверху и принятые за последние 14 дней. Счётчик в меню — просрочки плюс
заявки на срок и непринятые продления обоих видов.

**Продление ВМ.** `POST /vms/{id}/extend` с телом `{expected_return_at, comment?}`: автор, участник команды или админ
(админка продлевает ВМ тем же маршрутом). Разрешено для ВМ в статусах `queued`, `creating`, `ready`, `failed`;
`deleting` и `deleted` — 409. Новый срок не в прошлом (422) и позже текущего (409; у ВМ без срока — с сегодняшнего
дня). Строка ВМ блокируется `FOR UPDATE`, как при отказе, чтобы не мешать worker'у. Продление пишется в тот же журнал
`booking_extensions` (`vm_id`) с той же отметкой «Принято»; новый срок попадает в объект ВМ в Insight (запись выше), событие `asset_events` не
создаётся (журнал привязан к ПК). Описание ВМ в vCenter (срок в Notes) обновляет worker: когда `expected_return_at` расходится с `notes_return_at`, он перезаписывает аннотацию (до 10 ВМ за круг, при ошибке повторит на следующем). В ответах
`/admin/extensions` у записи есть `kind` (`pc` / `vm`), `name` и один из объектов `booking` / `vm`.

Раз в сутки после 10:00 worker шлёт сводку просрочек в Mattermost, если задан `MATTERMOST_WEBHOOK_URL`: ПК и ВМ с
командой, арендатором, сроком и числом дней (до 30 записей каждого вида).

**Напоминания о конце срока** (DR-15060, «Окончание срока»). Раз в рабочий день после 10:00 worker шлёт в тот же канал
Mattermost ПК и ВМ (`ready` / `failed`), у которых до конца срока осталось 5 рабочих дней, и те, у кого сегодня последний
рабочий день срока (срок в выходные — напоминание в пятницу). В выходные и праздники не шлёт; отправку отмечает в
`app_settings` (`term_reminders_last`). Рабочие дни считаются по производственному календарю `backend/config/work_calendar.yaml`
(`WORK_CALENDAR_FILE`, модуль `core/workdays.py`): субботы и воскресенья — выходные, `holidays` — праздники и переносы,
`workdays` — рабочие выходные; файл читается с диска при каждом расчёте и правится без пересборки. Личные сообщения
заказчику — когда появится бот Mattermost.

## Данные для планирования

«Обзор парка» показывает под сводкой два блока. «Простой серверов» (`GET /admin/idle`): свободные ПК опубликованных
пулов (не в архиве) с давностью последней выдачи; простой считается от возврата последней брони, а если ПК не
выдавали, от появления в учёте; API отдаёт все такие ПК, самые долгие первыми, а блок показывает 10 и раскрывает
остальные кнопкой «Показать все».
«Мощности кластера» (`GET /admin/cluster`): свободные и общие процессор, память и хранилище кластера ВМ из vCenter.
«Номера ВМ» (`GET /admin/vm-numbers`): сколько свободных объектов Insight (тип Virtual, «На складе»), не занятых живыми ВМ,
осталось для имён виртуалок; при 5 и меньше (`LOW_VM_NUMBERS` в `services/vms.py`) блок предупреждает, при нуле пишет, что
заказы ВМ отклоняются; если Insight недоступен, вместо числа причина. Блок опрашивает Insight, поэтому обновляется раз в 5 минут.

## Расхождения («Требуют внимания»)

* ПК закреплён за отделом, а в Insight он «ТО» / «Списано» / пропал из выборки;
* включена запись в Insight, а там ПК всё ещё «Ожидает»;
* истёк срок возврата;
* последняя запись в Insight завершилась ошибкой.

## Категории мощности

Порядок определения: ручная категория админа → поле категории из Insight (если включено в
маппинге) → автоматические правила по ОЗУ и видеокарте (`TIER_*` в `.env`):
ВМ — по типу объекта; «мощный» — от 32 ГБ ОЗУ или GPU из списка (RTX, 1660…); «средний» — от 16 ГБ
или GPU уровня 1050/1650; остальное — «слабый». В каталоге слабые начинаются от 8 ГБ ОЗУ
(`TIER_WEAK_MIN_RAM_GB`): ПК с меньшей памятью сотрудникам не показываются, админ видит их в «Инвентаризации».

## Доставка и окружения

* **Разработка и демо:** `docker-compose.yml` собирает образы из исходников, режим `INSIGHT_MODE=mock`. Описание сервисов,
  общее для dev и прода, лежит в `docker-compose.base.yml` (подключается через `extends`); в `docker-compose.yml` и
  `docker-compose.prod.yml` остаются `build` или `image` и монтирование кода.
* **CI** (GitHub Actions, `.github/workflows/ci.yml`): тесты backend и frontend (правило пропуска — `AGENTS.md`,
  «Тесты»), проверка конфигов (`deploy.sh`, compose, nginx) и публикация образов `ghcr.io/reebakov/hms-rent-backend` и
  `-frontend` с тегом-sha коммита.
* **Прод:** `docker-compose.prod.yml` на готовых образах, обновление командой `sudo ./scripts/deploy.sh` (порядок шагов
  и откат — `README.md`, «Деплой на сервер»). С диска сервера читаются только `backend/config` и, для HTTPS, `deploy/nginx/tls.conf`,
  `frontend/nginx/app.inc` и сертификат.
* **HTTPS:** `docker-compose.tls.yml` подключается сам, если есть `certs/fullchain.pem` и `certs/privkey.pem`
  (`docs/DOMAIN_TLS.md`; на проде включён с 20.10.2026). Секреты и права файлов — `docs/SECRETS.md`.
