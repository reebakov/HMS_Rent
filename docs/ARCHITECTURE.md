# Архитектура HMS Rent

## Компоненты

```
 Браузер ──► frontend (nginx: SPA, прокси /api, HTTPS) ──► backend (FastAPI) ──► PostgreSQL
                                                                │  ▲                 ▲
   Bouncer ◄── вход (OIDC) ─────────────────────────────────────┤  │                 │
   Jira Service Desk ◄── создание заявок и переписка ───────────┘  │                 │
                                                                    │                 │
   Jira Insight ◄── чтение и запись ─┐                              │                 │
   Jira Service Desk ◄── статусы ────┼──────────────── worker ──────┴─────────────────┘
   vCenter ◄── клон и удаление ВМ ───┤        (синхронизация, запись в Insight, очередь ВМ,
   Mattermost ◄── уведомления ───────┘         статусы заявок, сводка просрочек)
```

* **backend** — REST API `/api/v1/*`, не хранит состояние, можно запускать несколько копий. При старте контейнера
  применяет миграции (`alembic upgrade head`).
* **worker** — один процесс с циклом раз в 5 секунд. Шаги цикла выполняются по очереди, ошибка одного шага пишется в
  лог и не останавливает остальные:
  1. синхронизация с Insight (если подошло время, защищена advisory-lock в Postgres, поэтому кнопка «Синхронизировать
     сейчас» во время планового прогона ничего не ломает);
  2. запись изменений в Insight;
  3. очередь виртуальных машин: создание (до 2 за круг), удаление (до 5), обновление IP;
  4. обновление статусов заявок Service Desk (раз в 2 минуты на заявку);
  5. ежедневная сводка просрочек в Mattermost.
* **frontend** — статическая сборка React, nginx отдаёт её и проксирует `/api` на backend. Если на сервере есть
  сертификат, nginx принимает HTTPS (подробности в «Доставка и окружения»).

## Кто источник правды

| Данные | Источник | Почему |
|---|---|---|
| Список ПК, характеристики, «железный» статус (свободен / ремонт / списан) | **Insight** | там уже ведётся учёт, портал его не дублирует вручную |
| Бронирования: отдел, ответственный, даты | **БД портала** | история выдачи и инвентаризация по отделам |
| Виртуальные машины | **vCenter** (сама ВМ) и **БД портала** (заявка, владелец, статус) | ВМ создаёт и удаляет worker, в БД остаётся история |
| Статус заявки в Service Desk и публичные комментарии | **Jira** | портал хранит ключ заявки и последний известный статус, комментарии читает по запросу |
| Справочник отделов | **БД портала** | выбор из списка, а не свободный текст: отчёты не разваливаются на «QA» / «qa» / «Отдел QA» |
| Шаблоны ОС для конструктора ВМ, лимиты и интервалы | настройки на сайте (`app_settings`) | админ меняет без перезапуска, значения важнее `.env` |
| Роль администратора | файл `config/admins.txt` (рабочие почты из Bouncer) или локальная учётка из CLI | файл проверяется на каждом запросе: убрали почту — права пропали сразу |
| Что видно сотрудникам | **пулы выдачи** в БД портала | Insight не надо менять; админ управляет из интерфейса |

## Модель данных

| Таблица | Что хранит |
|---|---|
| `computers` | копия объекта Insight: характеристики, `insight_status`, все атрибуты в `attributes` (JSONB), категория `tier`, статус портала `status`, текущий отдел, `usage_until` и `order_number` текущей аренды |
| `bookings` | бронь: **номер заказа** (сквозной, общий с ВМ), ПК, отдел, аккаунт, имя и ник, цель, `booked_at`, `expected_return_at`, `returned_at`, кто вернул и комментарий |
| `virtual_machines` | заявка на ВМ и её жизненный цикл: имя, CPU, RAM, диск, статус, шаблон ОС (`template_key`, `os_label`), владелец, отдел, срок, `vsphere_moid`, IP |
| `service_requests` | заявки в Jira Service Desk: вид (`problem` / `return`), ПК или ВМ, ключ заявки, последний известный статус, ошибка создания |
| `asset_events` | журнал всего, что происходило с ПК: бронь, возврат, смена статуса в Insight, появление/исчезновение, правки админа, ошибки записи |
| `departments` | справочник отделов (название, код, руководитель, активен) |
| `pools`, `pool_departments` | пулы выдачи и отделы, которые их видят; `computers.pool_id` — в каком пуле ПК (нет пула — сотрудники его не видят) |
| `users` | сотрудники, создаются при первом входе (логин, ФИО, почта, роль, отдел, `auth_source`: `bouncer` / `local` / `dev`) |
| `sync_runs` | журнал синхронизаций с Insight; `details` (JSONB) — что именно изменилось в запуске |
| `app_settings` | настройки с сайта (ключ → JSON), в том числе список шаблонов ОС `vm_templates` |

Номера заказов даёт последовательность `rental_order_seq`: общая для ПК и ВМ, пропуски возможны.

Ограничение в БД: **у одного ПК не может быть двух активных броней** (частичный уникальный индекс
`uq_bookings_active_computer`), а сама бронь делается под `SELECT … FOR UPDATE` — двое не смогут
одновременно забрать один компьютер.

## Статусы компьютера на портале

| Статус | Откуда | В каталоге |
|---|---|---|
| `available` | Insight: «Ожидает» и нет активной брони | ✅ можно бронировать |
| `booked` | есть активная бронь на портале | — |
| `in_use` | Insight: «Используется», «В работе», «Исследования», «Проекты», «проект Events», «Эко», а брони нет (выдан мимо портала) | — |
| `maintenance` | Insight: «ТО», «Тест», «Резерв», «На складе», «Доставка», «На регистрации», «Frozen» | — |
| `retired` | Insight: «К закрытию», «Закрывается», «Закрыто», «Списано» | — |
| `unknown` | статус Insight не описан в `status_map` | — |

Соответствие статусов настраивается в `backend/config/insight_mapping.yaml`. Статус «железа»
меняется в Insight, портал только читает его. Исключение — запись в Insight при брони (ниже).

## Пулы выдачи

Синхронизация тянет из Insight всю «вселенную» по `query` — её видят только админы в инвентаризации.
Сотрудникам в каталоге показываются лишь ПК из **опубликованных пулов**. Пул наполняется списком
имён/ключей Insight или галочками в инвентаризации; ПК состоит максимум в одном пуле, каждое
перемещение пишется в журнал ПК. Скрыть пул — значит мгновенно убрать его ПК из каталога, не трогая брони.
Пул без отделов виден всем сотрудникам, с отделами — только им.

## Синхронизация (Insight → портал)

1. Worker раз в `insight_sync_interval_min` (настройка на сайте, по умолчанию 10 минут) забирает все объекты по
   запросу `query` из маппинга (с пагинацией).
2. Объекты сопоставляются с `computers` по `insight_object_id`, характеристики обновляются.
3. Если поменялся статус в Insight — пишется событие `insight_status_changed`.
4. ПК, пропавшие из выборки, **не удаляются**, а помечаются `is_archived` (история сохраняется).
5. Защита от ошибки в запросе: если Insight вернул 0 объектов, а в базе они есть, прогон
   считается ошибочным и ничего не архивирует.
6. Что изменилось в запуске, сохраняется в `sync_runs.details`: новые ПК, изменённые (поле: было → стало) и
   ушедшие в архив (до 500 записей на список; служебные атрибуты Insight вроде `Updated` не учитываются). На странице
   «Синхронизация» счётчики «Новых / Изменено / В архив» открывают эти детали (`GET /admin/sync/runs/{id}`).

## Обратная запись (портал → Insight), настройка `insight_writeback`

При брони/возврате у ПК ставится флаг `writeback_pending`. Worker в каждом круге (раз в 5 с) отправляет в Insight
**текущее** состояние: статус («Используется» / «Ожидает»), «Пул выдачи», «Команда-получатель»,
«Срок использования», «Номер заказа» (имена атрибутов — в `insight_mapping.yaml`, подробности — INSIGHT_SETUP.md, раздел 7) и снимает флаг. Если Insight недоступен, флаг остаётся и запись
повторится; ошибка видна в карточке ПК и в «Требуют внимания». Отправка идемпотентна: повтор ничего не испортит.
ВМ в Insight не записываются.

## Виртуальные машины и шаблоны ОС

Конструктор ВМ (карточка в каталоге) ставит заявку в очередь, worker создаёт машину в vCenter.

* **Жизненный цикл:** `queued → creating → ready → deleting → deleted`, ошибка — `failed`. Из `queued` отказ сразу
  `deleted`, из `ready` и `failed` — через `deleting` (worker выключает и удаляет ВМ). Из `creating` отказаться нельзя.
* **Создание:** worker клонирует шаблон из `vm_templates`, задаёт CPU, RAM, диск и описание (арендатор, отдел, срок).
  При ошибке делается **одна повторная попытка** через 10 секунд, после каждой неудачи недоделанный клон
  удаляется; после второй неудачи ВМ получает статус `failed` с текстом ошибки.
* **Шаблоны ОС** (`vm_templates` в `app_settings`, редактор в «Настройках»): ключ, название, ОС (`windows` / `linux`),
  имя шаблона в vCenter, спецификация гостевой настройки, минимальный диск, включён или нет. Шаблон без имени в
  vCenter показывается в конструкторе как «скоро» и недоступен для выбора. Диск не может быть меньше минимума
  шаблона и общего `vm_min_disk_gb`. Ключи шаблонов уникальны; `PATCH /admin/settings` с повторным ключом или
  неизвестной настройкой отклоняется (422).
* **Ограничения:** лимит ВМ на человека (`vm_max_per_user`), диапазоны CPU, RAM и диска (настройки на сайте). Имя
  уникально среди ВМ не в статусах `deleted` и `failed`.
* После перезапуска worker'а записи `creating` сверяются с vCenter по имени: нашлась — `ready`, нет — снова `queued`.

## Заявки в Jira Service Desk

Подробности настройки — `docs/SERVICE_DESK.md`. Включается заданным `SD_TOKEN` (или `SD_USERNAME`/`SD_PASSWORD`);
без него кнопки скрыты.

* **«Сообщить о проблеме»** у ПК и ВМ в «Моей аренде»: backend создаёт заявку типа `SD_REQUEST_TYPE_PROBLEM` с описанием
  проблемы и данными ПК или ВМ (имя, заказ, команда, арендатор, характеристики).
* **Возврат ПК** на сайте в фоне создаёт заявку типа `SD_REQUEST_TYPE_RETURN` (`SD_RETURN_ON_RETURN`). Название:
  `HMS Rent: возврат ПК <имя> (заказ №N)`. Ошибка Jira не мешает возврату и сохраняется в заявке.
* **От чьего имени:** сначала `raiseOnBehalfOf` = логин сотрудника; если такого пользователя в Jira нет, заявка
  создаётся от сервисной учётки, а имя и почта сотрудника попадают в описание.
* **Переписка:** публичные комментарии из Jira видны в портале (внутренние заметки агентов скрыты), ответ сотрудника
  уходит публичным комментарием `[HMS Rent] Имя: текст`. Статус открытых заявок worker обновляет раз в 2 минуты.
* **Доступ:** заявку видят и комментируют её автор, участники команды-получателя и администраторы.

## Просрочки

Бронь ПК с активным статусом и ВМ в статусах `ready` / `failed` считаются просроченными, если срок возврата раньше
сегодняшнего дня (по `DISPLAY_TIMEZONE`). Админка → «Просрочки» показывает их по убыванию дней просрочки, в меню есть
счётчик. Раз в сутки после 10:00 worker шлёт сводку в Mattermost, если задан `MATTERMOST_WEBHOOK_URL`: ПК и ВМ с
командой, арендатором, сроком и числом дней (до 30 записей каждого вида).

## Расхождения («Требуют внимания»)

* ПК закреплён за отделом, а в Insight он «ТО» / «Списано» / пропал из выборки;
* включена запись в Insight, а там ПК всё ещё «Ожидает»;
* истёк срок возврата;
* последняя запись в Insight завершилась ошибкой.

## Категории мощности

Порядок определения: ручная категория админа → поле категории из Insight (если включено в
маппинге) → автоматические правила по ОЗУ и видеокарте (`TIER_*` в `.env`):
ВМ — по типу объекта; «мощный» — от 32 ГБ ОЗУ или GPU из списка (RTX, 1660…); «средний» — от 16 ГБ
или GPU уровня 1050/1650; остальное — «слабый». В каталоге слабые начинаются от 8 ГБ ОЗУ
(`TIER_WEAK_MIN_RAM_GB`): ПК с меньшей памятью сотрудникам не показываются, админ видит их в «Инвентаризации».

## Доставка и окружения

* **Разработка и демо:** `docker-compose.yml` собирает образы из исходников, режим `INSIGHT_MODE=mock`.
* **CI** (GitHub Actions): тесты backend и frontend (пропускаются, если менялись только документация, скрипты и
  compose-файлы) и публикация образов `ghcr.io/reebakov/hms-rent-backend` и `-frontend` с тегом-sha коммита.
* **Прод:** `docker-compose.prod.yml` на готовых образах, обновление командой `sudo ./scripts/deploy.sh` (образы нужного
  коммита, дамп БД, перезапуск, проверка `/api/health`, автооткат). С диска сервера читаются только `backend/config`
  и, для HTTPS, конфиги nginx из `deploy/nginx` и сертификат.
* **HTTPS:** `docker-compose.tls.yml` подключается сам, если есть `certs/fullchain.pem` и `certs/privkey.pem`
  (`docs/DOMAIN_TLS.md`). Секреты и права файлов — `docs/SECRETS.md`.
