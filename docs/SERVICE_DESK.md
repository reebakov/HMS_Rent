# Заявки в Jira Service Desk

В «Моей аренде» у каждого ПК и виртуалки есть кнопка **«Сообщить о проблеме»**. Сотрудник описывает проблему →
в Service Desk создаётся заявка с данными ПК/ВМ, номером заказа и командой. Номер заявки и статус
видны прямо у ПК; по клику — переписка: публичные комментарии админов из Jira (обновляются сами) и поле для ответа.
Внутренние заметки агентов сотрудник не видит.

Возврат ПК на сайте автоматически создаёт заявку **«Возврат»** — её номер и статус видны в «Истории».
Бронь ПК создаёт заявку **«подготовить ПК»** с выбранной ОС, а форма **«Сборка по запросу»** в каталоге — заявку на сборку
(`SD_PREPARE_ON_BOOKING=false` отключает заявку при брони).
Все заявки портала создаются одним типом «Прочее» (`SD_REQUEST_TYPE`, 1252): обязательное поле у него одно — описание. В форме этого типа есть только описание (темы нет, Jira ставит название типа), поэтому при создании
портал отправляет одно поле — `description`, а сразу после создания правит шапку задачи: тему (`HMS Rent: …`) и поля из `SD_ISSUE_FIELDS`: компонент HMS и эпик DR-69 (Epic Link, как в DR-15373) для всех видов заявок. Если правка шапки не удалась, заявка остаётся, а причина — в логе backend.
В описании заявки «подготовить ПК» есть ссылка на страницу заказа в разделе «Исполнитель»
(`PUBLIC_URL/executor/orders/<id>`): там исполнитель вносит данные для подключения, и заказчик видит их в «Моей аренде».
Заявки видны всей команде-получателю.

**Проверочные заявки.** `SD_SUMMARY_PREFIX=ТЕСТ` добавляет слово в начало темы каждой заявки в Jira («ТЕСТ HMS Rent:
подготовить ПК …»), чтобы исполнители не брали её в работу; в портале тема остаётся без него. На проде префикс пуст;
если его временно включали для проверки, после неё строку убирают и применяют `.env` (`deploy.sh --redeploy`).

**Статусы для заказчика.** Заказчик видит не названия workflow Jira, а «Принят», «В работе», «Заморожено» (с комментарием
исполнителя), «Снято с исполнителя», «Выполнен», «Отклонён» (таблица — `docs/ARCHITECTURE.md`, раздел «Заявки в Jira
Service Desk»). Для «Снято с исполнителя» и резолюции портал читает историю задачи через REST Jira: сервисной учётке
нужны права «Просмотр проектов» и «Просмотр истории» в проекте DR. Проверка на конкретной задаче:
`python -m app.cli sd-transitions DR-123` — покажет, какие переходы доступны учётке и читается ли история.

## Настройка

1. Сервисная учётка в Jira — **агент** этого Service Desk (нужно, чтобы создавать заявки от имени сотрудников
   и читать комментарии). Personal Access Token → `SD_TOKEN` в `.env` (или `SD_USERNAME` и `SD_PASSWORD`).
   Номер Service Desk и тип заявок (`SD_SERVICE_DESK_ID`, `SD_REQUEST_TYPE`) берутся из адреса портала
   `…/desk/portal/<id>/create/<тип>`; значения по умолчанию — в `.env.example`. Применить `.env`: на проде
   `sudo ./scripts/deploy.sh --redeploy`, при разработке `docker compose up -d --force-recreate backend worker`.
2. Проверка: `docker compose exec backend python -m app.cli sd-check` (на проде — с `-f docker-compose.prod.yml`) —
   покажет поля типа заявок «Прочее».
   Портал заполняет **Тему (summary)** и **Описание (description)**; у типа «Прочее» других обязательных полей быть не должно,
   иначе Jira не примет заявку. Поля шапки (`SD_ISSUE_FIELDS`, JSON `{"поле Jira": значение}`: идентификатор поля — в
   `sd-check` или в карточке задачи) портал ставит отдельным запросом после создания; пустое значение отключает правку.
3. От чьего имени создаётся заявка и как устроена переписка — `docs/ARCHITECTURE.md`, раздел «Заявки в Jira
   Service Desk» (`SD_RAISE_ON_BEHALF`, `SD_RETURN_ON_RETURN` отключают эти режимы).

Открытая переписка на сайте обновляется раз в 15 секунд; статусы заявок обновляет worker (`docs/ARCHITECTURE.md`).
Без `SD_TOKEN` (или `SD_USERNAME` и `SD_PASSWORD`) кнопка «Сообщить о проблеме» скрыта.
