# Подключение Insight (jira.marvin-it.com)

Jira 8.15 (Server/DC) с Insight, схема **IT Assets** (`id=1`), тип **Automat** (`typeId=55`).
Маппинг уже настроен под неё: `backend/config/insight_mapping.yaml`.

## 1. Доступ: одна сервисная учётка на весь портал

Портал ходит в Insight сам, в фоне (синхронизация по расписанию) — без участия пользователей.
Поэтому нужен **один** доступ на портал, а не токен у каждого:

* сотрудники и админы Jira-учётки для портала не используют вообще;
* все правки делаются в портале, в Insight их отправляет портал от имени сервисной учётки;
* кто именно из админов что сделал — видно в журнале портала.

Варианты по убыванию надёжности:

1. **Personal Access Token сервисной учётки** (например, `svc-hmsrent`): Jira → профиль →
   *Personal Access Tokens* → *Create token*. В `.env`: `INSIGHT_TOKEN=…`
2. Логин/пароль сервисной учётки: `INSIGHT_USERNAME` / `INSIGHT_PASSWORD`.
3. **Без авторизации** — оставить всё пустым. Сработает, только если Jira отдаёт Insight анонимно
   (так могло быть в прошлых проектах). Проверка ниже покажет; для записи в Insight всё равно нужна учётка.

Права учётки: просмотр схемы IT Assets; для записи статусов — ещё и редактирование объектов.

## 2. Проверка подключения

```bash
# в .env: INSIGHT_MODE=live, JIRA_URL=https://jira.marvin-it.com, INSIGHT_TOKEN=…
docker compose up -d --build            # разработка; на проде: sudo ./scripts/deploy.sh --redeploy
docker compose exec backend python -m app.cli insight-check --sample 5
```

На проде команды `docker compose` выполняются с `sudo` и `-f docker-compose.prod.yml`.

Команда ничего не записывает в базу и покажет:

* под какой учёткой идут запросы (или что анонимно);
* схемы и типы объектов с количеством;
* **все статусы схемы** — впишите нужные в `status_map`;
* атрибуты типа и 5 объектов: как они лежат в Insight и как их понял портал (CPU / ОЗУ / GPU / диск /
  статус / категория).

## 3. Что берём из Insight

* **Запрос:** `objectType = "Automat" AND Type IN ("Physical", "Host Emulator")` — Guest Emulator
  исключены: это эмуляторы на хостах, а не компьютеры. Сколько объектов каждого типа:
  ```bash
  docker compose exec backend python -m app.cli insight-check --breakdown Type --query 'objectType = "Automat"'
  ```
* **Характеристики:** атрибуты «Процессор», RAM, «Диск», «Видеокарта», OS. Если они пустые —
  запасной вариант из Comment вида `Ryzen 7 2700 | 16GB | GTX 1650 | SSD 224GB /`.
* **Статусы** (`status_map` в маппинге): соответствие статусов Insight и портала — в `docs/ARCHITECTURE.md`,
  раздел «Статусы компьютера на портале».

## 4. Первая синхронизация

По умолчанию загружаются все объекты (`INSIGHT_MAX_OBJECTS=0`). Для пробного прогона можно ограничить выборку,
например `INSIGHT_MAX_OBJECTS=300` в `.env`: загрузятся первые 300 объектов. Админка → **Синхронизация** →
«Синхронизировать сейчас». Всё хорошо — верните `0` (или уберите строку).

## 5. Что увидят сотрудники

Синхронизация лишь наполняет инвентаризацию. **В каталоге сотрудников ничего не появится, пока
админ не добавит ПК в опубликованный пул** (Админка → «Пулы выдачи» → «Добавить ПК» списком имён
или галочками в «Инвентаризации»). Бронировать можно только ПК в статусе «Ожидает».

## 6. Запись в Insight

Портал меняет **атрибут Status** — при брони «Используется», при возврате «Ожидает» — и поля аренды из
раздела 7 (пул, команда, срок, номер заказа). Exploitation Status и другие атрибуты не читаются для выдачи и не меняются.

Включается переключателем «Запись статусов в Insight» в Админка → «Настройки» (стартовое значение — `INSIGHT_WRITEBACK`
в `.env`; когда значение задано на сайте, оно важнее `.env`). Сервисной учётке нужны права на редактирование объектов
IT Assets. ⚠️ При локальных тестах против боевой Jira каждая тестовая бронь реально меняет статус ПК —
включайте, когда будете готовы (или тестируйте на ПК, который не жалко «занять»).

## 7. Поля аренды: «Пул выдачи», «Команда-получатель», «Срок использования», «Номер заказа»

Четыре атрибута типа **Automat** синхронизируются в обе стороны. Имена атрибутов задаются в `insight_mapping.yaml`
(блок `attributes`: `pool`, `team`, `usage_period`, `order_number`) и должны совпадать с Insight буква в букву —
`python -m app.cli insight-check` покажет предупреждение, если какого-то атрибута нет у типа.

| Атрибут Insight | Insight → портал (при синхронизации) | Портал → Insight (запись включена) |
|---|---|---|
| **Пул выдачи** | значение определяет пул ПК. Пула с таким именем на портале нет — он создаётся **неопубликованным** (сотрудники его не увидят, пока админ не откроет его в «Пулах выдачи») | при добавлении ПК в пул / переносе / удалении пула пишется имя пула (пусто — ПК вне пулов) |
| **Команда-получатель** | для ПК, выданных мимо портала: ищется отдел с таким названием в «Отделах» портала | при брони — отдел брони; при возврате очищается |
| **Срок использования** | для ПК, выданных мимо портала: дата (понимаются `2026-10-20`, `20.10.2026`, `20/Oct/26`, `20/окт/26`) | при брони — «Вернуть до», при продлении — новый срок; при возврате очищается |
| **Номер заказа** | для ПК, выданных мимо портала: число | при брони — номер заказа брони; при возврате очищается |

Правила:

* **Номер заказа** — сквозной: 1, 2, 3 … для каждой выдачи компьютера **или** виртуалки (одна общая нумерация,
  PostgreSQL-последовательность `rental_order_seq`). Одновременные заказы не получат один номер; пропуски возможны,
  если заказ не оформился из-за ошибки. Существующим броням и виртуалкам номера присвоены миграцией `0005` по порядку создания.
  Номер виден сотруднику в «Моей аренде», админу — в журнале выдачи, инвентаризации, списке виртуалок и CSV.
* Пока изменения портала не доехали до Insight (флаг `writeback_pending`), значения из Insight для этого ПК не применяются.
* Пустой «Пул выдачи» в Insight пул на портале **не сбрасывает** — убрать ПК из пула можно только на портале.
  Если пулы уже назначены на портале, а в Insight поле пустое, один раз выполните:
  ```bash
  docker compose exec backend python -m app.cli push-pools    # на проде — с -f docker-compose.prod.yml
  ```
* **Пул по умолчанию.** `INSIGHT_DEFAULT_POOL=Общий пул` (пусто — выключено): свободный ПК («Ожидает»), у которого
  «Пул выдачи» пуст и в Insight, и на портале, при синхронизации попадает в этот пул, а при включённой записи пул
  уходит в Insight. Пул должен существовать на портале, иначе в логе предупреждение. Пул из Insight и уже назначенный
  на портале важнее; ПК в других статусах (используется, ремонт, очистка) и виртуальные не затрагиваются. Вручную
  убранный из пулов свободный ПК вернётся в пул по умолчанию при следующей синхронизации, поэтому скрывать его нужно
  неопубликованным пулом.
* Если поле аренды записать не удалось (опечатка в имени атрибута, тип «Select» без такого значения и т. п.), **статус
  всё равно записывается**, а ошибка видна админу в «Инвентаризации» («Ошибка записи в Insight»).
  Лучше делать «Пул выдачи», «Команда-получатель» и «Номер заказа» текстовыми атрибутами (или ссылкой на объект —
  тогда значение ищется по названию), а «Срок использования» — типом Date.

## 8. Номера и объекты ВМ

Имя виртуалки не вводится: портал берёт его у свободного объекта Insight (`A1###`). Нужны объекты-заглушки типа
**Automat** с `Type = Virtual` и статусом «На складе». Запрос задаёт `vm_free_query` в `insight_mapping.yaml`:

```
objectType = "Automat" AND "Status" IN ("На складе") AND "Type" IN ("Virtual")
```

* При заказе ВМ портал выбирает свободный объект с наименьшим номером, который не занят живой ВМ портала; его имя
  становится именем ВМ в vSphere и на портале. Нет свободных номеров или Insight недоступен — заказ отклоняется с
  понятным текстом (сотруднику детали Insight не показываются, они в логе backend).
* Один объект не может достаться двум живым ВМ (частичный уникальный индекс в БД). Номер освобождается, когда ВМ
  удалена или заказ упал с ошибкой.
* Запись в объект ВМ идёт тем же переключателем `insight_writeback`, что и для ПК: заказ → «Используется», команда,
  срок, номер заказа и IP; удаление или ошибка → «На складе» и пустые поля (имена атрибутов — `team`,
  `usage_period`, `order_number`, `ip_address` из блока `attributes`; статусы можно переопределить в
  `writeback.vm_status_values`). Если запись выключена, портал всё равно не выдаёт один номер дважды, но в Insight
  объекты остаются «На складе».
* Прежние ВМ с именами `rent-…` объектов Insight не имеют и в Insight не пишутся.
* В режиме `INSIGHT_MODE=mock` номера демонстрационные: `A1001…A1050`.
