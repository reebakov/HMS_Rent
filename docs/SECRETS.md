# Секреты и чувствительные данные

Где хранятся секреты и персональные данные, какие права должны быть и что менять при утечке. Схема сегодня простая:
файл `.env` на сервере, без отдельного хранилища секретов.

## Где что лежит

| Что | Где | Правильные права | Содержимое |
|---|---|---|---|
| `.env` | `/opt/hms-rent/.env` | `600`, владелец `root` | пароль БД, `SECRET_KEY`, секрет клиента Bouncer, токен или пароль Insight, пароль vCenter, webhook Mattermost |
| Бэкапы БД | `/var/backups/hms-rent/*.sql.gz` | каталог `700`, файлы `600` | всё содержимое БД: почты и имена сотрудников, брони, события, хэши паролей локальных админов (scrypt), настройки |
| Данные БД | Docker-том `pgdata` | под управлением Docker (root) | то же, что в дампах |
| Окружение контейнеров | `docker inspect`, `docker exec … env` | доступно root и тем, кто использует `sudo` или группу `docker` | значения из `.env` |
| Ключ TLS | `certs/privkey.pem` | `600`, владелец `root` | приватный ключ сертификата (см. `DOMAIN_TLS.md`) |
| Ключи и токены разработчика | `~/.ssh/*`, `~/.config/gh/hosts.yml` | `600` | ключ доступа к серверу, токен GitHub |

Секретов нет в git (`.env` и `certs/` в `.gitignore`, остаётся только `.env.example` с демо-значениями), в образах
(`.dockerignore` исключает `.env`), в Jira, Confluence и сообщениях коммитов. Приложение не пишет секреты в логи,
ошибки и ответы API: для Insight и Bouncer это проверяется тестами. Репозиторий и образы в GHCR публичные, поэтому
всё, что попадает в них, считается опубликованным (в образе лежат `backend/config/*`: почты админов и имена атрибутов
Insight, это не секрет).

## Что делает `deploy.sh`

- Каталог бэкапов создаётся с правами `700`, новые дампы пишутся с `umask 077` (файлы `600`), старые дампы при каждой
  выкатке закрываются до `600`.
- Если у `.env` или `certs/privkey.pem` права шире владельца, скрипт предупреждает и показывает команду
  `sudo chmod 600 …`. Сами права он не меняет.

## Что настроить на сервере один раз

Маску `*.sql.gz` под `sudo` оболочка раскрывает от вашего пользователя, а после `chmod 700` каталог ему не виден, поэтому
файлы закрываются через `find` (он работает от `root`).

```bash
sudo chmod 600 /opt/hms-rent/.env
sudo chmod 700 /var/backups/hms-rent && sudo find /var/backups/hms-rent -name '*.sql.gz' -exec chmod 600 {} +
sudo chmod 600 /opt/hms-rent/certs/privkey.pem        # когда появится сертификат
```

## Ротация секретов

После любой правки `.env` выполните `sudo ./scripts/deploy.sh --redeploy`.

| Секрет | Как заменить | Последствия |
|---|---|---|
| `SECRET_KEY` | новое значение `openssl rand -hex 32` в `.env` | текущие сессии сбрасываются, пользователи входят заново |
| `POSTGRES_PASSWORD` | сначала `sudo docker compose -f docker-compose.prod.yml exec db psql -U hmsrent -c "ALTER USER hmsrent PASSWORD '<новый>'"`, затем тот же пароль в `.env` | пароль пользователя БД задаётся при первом создании тома, одной правки `.env` недостаточно: без `ALTER USER` backend не подключится |
| `BOUNCER_CLIENT_SECRET` | выпустить новый секрет клиента `hms-rent` в Bouncer (менеджер клиента или админы Bouncer) | до обновления `.env` вход через Bouncer не работает |
| `INSIGHT_TOKEN` или `INSIGHT_USERNAME` и `INSIGHT_PASSWORD` | перевыпустить токен или сменить пароль в Jira | пока не обновлён `.env`, синхронизация с Insight падает |
| `VCENTER_PASSWORD` | сменить пароль сервисной учётки vCenter | до обновления `.env` конструктор ВМ не работает |
| `MATTERMOST_WEBHOOK_URL` | создать новый webhook, старый удалить | уведомления шли бы в старый канал |
| Ключ TLS | перевыпустить сертификат, заменить `certs/*`, `nginx -s reload` | см. `DOMAIN_TLS.md` |
| SSH-ключ разработчика | убрать публичный ключ из `~/.ssh/authorized_keys` на сервере, выпустить новый | старый ключ теряет доступ |

**Если секрет мог прочитать посторонний** (например, `.env` или дамп были доступны всем локальным пользователям):
заменяйте все секреты из `.env`, а `SECRET_KEY` в первую очередь. Дамп содержит хэши паролей локальных админов, их
тоже нужно сменить (`python -m app.cli set-password <логин>`).

## Правила

- Секреты только в `.env` на сервере (права `600`) и в самих внешних системах. Не в git, не в чате, не в задачах Jira.
- Для каждой внешней системы своя сервисная учётка с минимальными правами. Личные и тестовые учётки в проде не
  используются.
- Новая переменная с секретом: поле в `core/config.py`, строка в `.env.example` с пустым значением, строка в таблице
  ротации выше.

## Открытый вопрос

Отдельное хранилище секретов (корпоративный Vault, если есть, иначе Docker Secrets из файлов) не выбрано. Пока
используется `.env` с правами `600`; выбор зависит от того, есть ли в компании Vault и какой CI используется.
